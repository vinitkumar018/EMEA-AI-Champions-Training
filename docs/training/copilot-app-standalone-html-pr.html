Before you start

Set a safe, clear scope

Choose a small training deliverable such as a self-contained HTML explainer. Decide what it should teach, who will use it, and which constraints matter: a single file, no external assets or data, accessible controls, and a clear visual style.

Safety: keep sensitive data out of training outputs Use only synthetic or sample figures in public training examples. For Highly Confidential workbooks, process them only through authorized local workflows. Never attach, upload, stage, commit, publish, or share those workbooks—or any generated HTML or CSV containing their data. Do not bypass labels or access controls. A file being stored locally does not make it safe to commit or share.

Local file use

A file can stay on your machine for private review or authorized local processing. Treat its contents according to their classification.

Repository use

Only add files that are approved for this repository and its audience. Review the exact diff before staging or committing.

1

Choose your workspace

Open the training repository in Copilot App

  1. Start the GitHub Copilot App and sign in to the account that has access to your training repository.
  2. Open or select the repository using the app's repository/project picker. The entry point may be named differently across app versions; choose the option that opens an existing local repository or repository project.
  3. Confirm the repository name and current branch shown for the workspace before asking Copilot to make changes. If you have not cloned it yet, use the app's supported clone/open flow.
No VS Code required Keep the repository open in Copilot App. Use its chat, change review, file preview, and GitHub pull-request features where available. If a button or panel name differs, look for the equivalent repository, changes, or pull-request action in your app version.
2

Ask for a focused change

Describe the HTML deliverable and its constraints

Tell Copilot what to create, where it belongs, and how you will verify it. Ask for a single ordinary HTML file—not a generated project, build setup, or bundle. Mention the audience, accessibility needs, allowed content, and anything that must stay out of version control.

Example prompt — replace bracketed text with non-sensitive details

In this training repository, create one self-contained HTML tutorial at [approved repository path] for [audience and learning goal]. Use inline CSS and only the JavaScript needed for the requested interaction. Do not add a framework, package, build step, external asset, or external data. Use synthetic sample content only; do not include confidential source data. Keep it accessible and responsive. After editing, summarize the file and tell me how to preview it and inspect the complete diff. Do not commit or open a pull request yet.
  • Give an exact destination path or ask Copilot to recommend one based on the repository structure.
  • State the output format and boundaries: one HTML file, no framework or external dependencies, and no unrelated edits.
  • Have Copilot explain any assumptions before broadening the change. Review those assumptions rather than accepting them automatically.
3

You are the reviewer

Inspect the generated file and complete diff

When Copilot is done, open the app's changes/diff view (or its equivalent) and inspect every changed file and hunk before accepting the result.

  • Confirm the only intended addition or edit is the approved HTML file; investigate unexpected files, generated assets, or dependency changes.
  • Read the HTML, CSS, and JavaScript. Check that the page is self-contained, links and controls make sense, and no confidential or real business data appears.
  • Review deletions and context as well as additions. Ask Copilot for a specific correction if something is wrong, then inspect the updated diff again.
  • Do not stage or commit a file just because Copilot created it. The diff is the decision point for what enters the repository.
4

Check the actual page

Preview and verify the HTML

Use the app's HTML/file preview if available, or open the approved local HTML file in a browser using the workspace's reveal/open-file action. The app UI may vary; if preview is unavailable, use another authorized local browser workflow and return to the app to review and commit.

  • Check the page at a narrow and a wide viewport; confirm there is no clipped content or horizontal overflow.
  • Use keyboard navigation, verify visible focus, and make sure headings, links, labels, and interactive controls are understandable.
  • Try each interactive element and inspect the browser console if the local preview exposes it.
  • Keep previewing local distinct from sharing: opening a local file does not add it to Git, but a commit or PR can make its contents available to repository collaborators.
Not sure whether preview is local? Check where the page opens and what data it loads. Do not upload sensitive inputs to get a preview; use only the authorized local workflow for that material.
5

Keep the work isolated

Create or confirm a feature branch

Before committing, confirm the repository's base branch and put the tutorial change on a feature branch. Use the app's branch control or Git changes workflow; labels vary between versions.

  • Choose a short name that describes the change, such as training/html-copilot-guide.
  • Verify the workspace is on that feature branch, not the default branch.
  • Check the final diff once more and stage only the intended, approved file. Leave unrelated or sensitive local files unstaged.
6

Save the reviewed change

Commit to the feature branch

Use the app's commit action in the repository changes view. Write a concise message that describes the tutorial, then confirm the commit target is your feature branch.

Commit is not the same as keeping a local draft A commit records the selected content in Git. Pushing the branch and opening a pull request shares it with the repository's review process. If you only need a local draft, do not stage, commit, or push it.
7

Request review

Create and review the pull request

  1. Push/publish the feature branch when prompted, then use the app's create-pull-request action or its equivalent.
  2. Confirm the base is the repository's intended default branch and the compare branch is your feature branch.
  3. Write a clear title and a short description of the tutorial, its audience, and what was checked. Include only safe, non-sensitive details.
  4. Before creating, review the PR's changed-files list and summary. Confirm it contains only the intended HTML/documentation changes and no confidential content.

If the app does not expose PR creation for this workspace, use its GitHub repository/pull-request handoff or the GitHub web interface; keep the same base/compare and diff checks.

8

Finish the review loop

Respond to CI and reviewer feedback

  • Check the PR's status checks and review comments in the app or on GitHub. If checks are pending, wait for their result before treating the PR as ready.
  • For a failure or comment, understand the requested change, make a focused fix on the same feature branch, and inspect the new diff.
  • Run the relevant checks again, commit and push the update, then reply to reviewers with what changed or why you disagree.
  • Confirm required approvals and checks are complete. Follow repository policy for merge; creating a PR does not mean it is approved or merged.

Use your repository's contribution, data-handling, and review policies whenever they are stricter than this tutorial.
